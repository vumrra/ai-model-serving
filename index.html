모델 설정은 별도 Argo Application이 추적한다. 모델 파라미터 변경마다 Gateway 이미지를 다시 빌드하지 않는다.

실제 요청Mac / LAN→ Windows :8000→ portproxy · forward→ FastAPI Gateway→ KServe Service · vLLM

왜 이 구조인가?

Gateway는 인증·요청 제한·모델 별칭을, vLLM은 추론을 담당한다. Argo CD는 Git에 고정한 이미지와 모델 설정을 클러스터에 반영한다. 수동 명령 대신 어떤 코드와 설정을 실행하는지 추적할 수 있는 배포를 택했다.

이 구조가 해결하지 않는 것

GitOps 자체가 token/s를 높이지는 않는다. GPU 한 장에 모델 replica 1, Recreate 전략이므로 모델 교체 때 중단될 수 있다. 여기서 구축한 API는 Private LAN용이며, 이 보고서를 공개하는 GitHub Pages와는 별개다.

4.8% 증가 · TPOT는 약 92.7ms로 유지

왜 이렇게 해석하는가? 입력을 처리하는 prefill과 토큰을 하나씩 만드는 decode는 다른 단계다. Prefix caching은 같은 입력 앞부분의 계산을 재사용하지만, 새 토큰을 생성하는 decode 자체를 빠르게 만들지는 않는다. 첫 응답은 크게 줄고 TPOT는 거의 같았던 결과는 이 원리와 일치한다. 단, 메모리 설정도 함께 바뀌었으므로 원인별 기여도는 분리되지 않았다.

공유되는 긴 입력에서는 차이가 더 컸다

평균 입력 533토큰의 공유-prefix 요청을 각 30회 보냈다. 이전 → 최종 구성에서 TTFT p95는 3,955.8 → 246.9ms, 처리량은 6.54 → 10.64 tok/s였다. 같은 시스템 프롬프트·문서 앞부분을 반복하는 요청에서 재사용할 계산이 많았던 사례다.

재사용할 입력이 없다면 다른 문제다

이전 구성의 평균 587토큰 긴 입력은 TTFT p95 3,939.1ms였다. 긴 입력을 읽는 비용은 짧은 채팅 결과에 드러나지 않는다. 공유-prefix 실험의 개선을 매번 다른 문서나 긴 프롬프트에도 그대로 적용할 수는 없다.

05

이 설정으로 해결되지 않은 것

01 / VRAM 여유는 겨우 기준을 넘었다

여유 521MiB는 6144 − reserved 178 − peak 5445로 계산한 보수적 추정이다. 512MiB 기준보다 9MiB 높다. 다른 GPU 작업을 동시에 실행해도 안전하다는 뜻이 아니며, 직접 free 메모리를 수집해 다시 볼 필요가 있다.

02 / p95가 좋아도 간헐적 지연은 남았다

약 33분의 최종 지속 부하에서 HTTP 360/360 성공, 처리량 10.50 tok/s였다. 하지만 요청별 지연 목표는 358/360만 만족했고, 첫 측정 요청 TTFT는 14.9초였다. 원인은 아직 분리하지 못했다.

03 / 추론 Pod와 컨트롤러의 안정성은 달랐다

etcd 저장 지연 → API timeout → leader lease 실패와 KServe manager 재시작이 관찰됐다. 후속 누적 restart는 6 → 11. 같은 시점 predictor와 Gateway는 restart 0이었다. 저장 지연의 근원이 WSL·Docker·host I/O 중 어디인지는 미확정이다.

04 / 큰 모델과 다중 사용자는 별도 선택이다

seq2는 총량을 늘렸지만 TPOT 목표를 넘었고, 4B AWQ는 더 느린 대신 얻는 품질 이득을 보여주지 못했다. 30개 규칙 평가는 작고 일부 재현 메타데이터도 부족하다. 더 큰 GPU의 성능이나 일반적인 모델 우열까지 이 결과로 판단할 수 없다.

결론

한 사용자·짧은 채팅·6GB GPU라는 조건에서 1.7B FP16을 유지하고 메모리와 캐시 설정을 조정하는 편이 합리적이었다. 첫 응답은 빨라졌고 메모리 여유도 늘었지만, 생성 속도는 거의 그대로다. 다음 과제는 최종 Gateway 경로 재측정, 캐시 단독 비교, 컨트롤 플레인 저장 지연 원인 분리다.
