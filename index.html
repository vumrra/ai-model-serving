AI 모델 서빙을
이해했다는 것은 무엇인가?

“AI 모델 서빙 구조와 추론 최적화를 이해하고 CI/CD로 실제 API 배포까지 연결하려면 무엇을 검증해야 하는가?” GPU에 모델을 올리는 데서 끝내지 않고, 요청이 처리되는 원리와 최적화의 대가를 실험으로 확인한 스터디 노트다.

이 문서의 답: 요청 경로를 설명하고, 입력 처리·토큰 생성·대기열의 병목을 구분하고, 메모리·속도·품질의 교환 관계를 같은 조건의 실험으로 확인해야 한다. 마지막으로 코드·모델·설정을 버전으로 고정해 실제 API까지 전달해야 한다. 이 PC의 설정값을 외우는 것이 아니라, 다른 환경에서도 이 판단 과정을 재사용하는 것이 목표다.

실험 환경: Windows · WSL2 · GTX 1660 6GB · Qwen3 · vLLM 0.8.5/V0. 저장된 측정 결과를 바탕으로 원리와 적용 조건을 설명한다.

모델 설정은 별도 Argo Application이 추적한다. 모델 파라미터 변경마다 Gateway 이미지를 다시 빌드하지 않는다.

실제 요청Mac / LAN→ Windows :8000→ portproxy · forward→ FastAPI Gateway→ KServe Service · vLLM

왜 이 구조인가?

Gateway는 인증·요청 제한·모델 별칭을, vLLM은 추론을 담당한다. Argo CD는 Git에 고정한 이미지와 모델 설정을 클러스터에 반영한다. 수동 명령 대신 어떤 코드와 설정을 실행하는지 추적할 수 있는 배포를 택했다.

이 구조가 해결하지 않는 것

GitOps 자체가 token/s를 높이지는 않는다. GPU 한 장에 모델 replica 1, Recreate 전략이므로 모델 교체 때 중단될 수 있다. 여기서 구축한 API는 Private LAN용이며, 이 보고서를 공개하는 GitHub Pages와는 별개다.

요청 한 개의 내부를 펼쳐 보면

요청 처리인증·입력 검사→ 템플릿·토큰화→ 대기열·스케줄러→ prefill→ decode 반복→ 토큰을 문자열로 변환·SSE 전송

Prefill과 decode는 무엇이 다른가?

Prefill은 입력 토큰을 처리해 생성에 필요한 상태를 만든다. Decode는 이전 문맥을 참조하며 새 토큰을 순차적으로 만든다. TTFT는 첫 토큰이 도착할 때까지이므로 prefill뿐 아니라 대기열·통신 비용도 포함한다. TPOT는 요청별 평균 생성 간격이다. “TTFT가 높다 → 무조건 캐시”가 아니라 어느 구간이 길어졌는지 먼저 나눠 봐야 한다.

KV cache는 모델 가중치와 다르다

가중치는 학습된 모델 파라미터이고, KV cache는 요청 문맥의 attention 계산 결과다. 일반적인 Transformer에서는 문맥과 동시 요청이 늘수록 KV 메모리도 커진다. 전체 VRAM에는 가중치 + KV cache + 실행 중간값·워크스페이스·graph 관련 할당이 들어간다. 가중치 양자화와 KV cache 양자화는 서로 다른 설정이다.

개념 근거: vLLM 내부 구조 해설. 여기서는 병목의 후보를 설명한다. prefill은 항상 compute-bound, decode는 항상 memory-bound라고 단정하지 않는다. 모델·배치·문맥에 따라 달라지며 이 PC에서 커널 프로파일링으로 병목을 확정한 것은 아니다.

02

어떤 이해를, 어떤 실험으로 확인했는가?

검증 항목은 제품이 실패할 수 있는 지점에서 나온다. 요청 경로가 틀리면 API가 아니고, 병목을 잘못 짚으면 튜닝이 아니며, 결과가 좋아도 같은 버전을 배포하지 못하면 재현 가능한 서비스가 아니다.

이해해야 할 개념확인하려던 질문실제 실험·관찰얻은 결론 / 남은 경계
서빙 계층의 책임엔진 실행과 사용 가능한 API는 어떻게 다른가?Gateway 경유 채팅·스트리밍과 Windows LAN 접근.API 정책과 추론 엔진을 분리했다. LAN 성공은 인터넷 공개·보안 운영 완성을 뜻하지 않는다.
Prefill과 decode첫 응답 개선과 생성 속도 개선은 같은가?메모리·캐시 변경 후 TTFT 498.2 → 225.9ms, TPOT 약 92.7ms 유지.첫 응답과 생성 간격이 다르게 움직임을 확인. 캐시 단독 기여도는 미분리.
KV 메모리와 모델 표현모델 적재만 성공하면 충분한가?메모리 비율 조정, 1.7B FP16과 4B AWQ 후보 비교.적재 가능성과 응답성·품질은 별도. 같은 모델의 양자화 A/B는 아니다.

비교 실험과 인과관계결과 차이가 정말 변경 때문인가?입력·출력 예산·thinking 조건을 맞춰 대표 구성을 반복.구성 선택 근거는 확보. 여러 변수를 함께 바꾼 결과를 단일 기법의 효과로 주장하지 않는다.
재현 가능한 배포선택한 구성이 실제 API에 전달됐는가?코드 → GHCR digest → GitOps 커밋 → Argo sync → API 응답.배포 연결은 확인. 최종 Gateway 성능 회귀 gate·실패 배포 rollback 훈련은 별도 과제.
보편적인 것은 질문이지, 숫자가 아니다. TTFT·TPOT·처리량·메모리·품질을 함께 보는 접근은 재사용할 수 있다. 반면 TTFT p95 ≤1초, TPOT p95 ≤100ms, 여유 VRAM ≥512MiB는 단일 사용자 채팅과 6GB GPU에 대해 이 실험이 정한 목표다. 업계 공통 합격선이나 사용자 조사로 입증한 값은 아니다.

HTTP 성공과 쓸 만한 응답도 다르다. 최종 지속 부하는 HTTP 360/360 성공이었지만 요청별 지연 기준은 358/360이었다. 전체 처리량 외에 목표 지연을 만족한 처리량인 goodput도 봐야 한다. TPOT p95는 요청별 평균 생성 간격의 p95이며, 모든 토큰의 실제 간격 분포(ITL)를 직접 측정한 값은 아니다.

4.8% 증가 · TPOT는 약 92.7ms로 유지

왜 이렇게 해석하는가? 입력을 처리하는 prefill과 토큰을 하나씩 만드는 decode는 다른 단계다. Prefix caching은 같은 입력 앞부분의 계산을 재사용하지만, 새 토큰을 생성하는 decode 자체를 빠르게 만들지는 않는다. 첫 응답은 크게 줄고 TPOT는 거의 같았던 결과는 이 원리와 일치한다. 단, 메모리 설정도 함께 바뀌었으므로 원인별 기여도는 분리되지 않았다.

공유되는 긴 입력에서는 차이가 더 컸다

평균 입력 533토큰의 공유-prefix 요청을 각 30회 보냈다. 이전 → 최종 구성에서 TTFT p95는 3,955.8 → 246.9ms, 처리량은 6.54 → 10.64 tok/s였다. 같은 시스템 프롬프트·문서 앞부분을 반복하는 요청에서 재사용할 계산이 많았던 사례다.

재사용할 입력이 없다면 다른 문제다

이전 구성의 평균 587토큰 긴 입력은 TTFT p95 3,939.1ms였다. 긴 입력을 읽는 비용은 짧은 채팅 결과에 드러나지 않는다. 공유-prefix 실험의 개선을 매번 다른 문서나 긴 프롬프트에도 그대로 적용할 수는 없다.

05

최적화 기법의 원리와 적용 조건

최적화 기법마다 줄이려는 비용이 다르다. 반복 입력의 계산, 요청 대기, 메모리 사용, GPU 실행 비용 중 어디가 문제인지에 따라 후보를 고른다. 아래 표는 작동 원리 → 적용 조건 → 측정 항목 → 이번 실험 범위를 연결한다.

실험은 vLLM 0.8.5/V0, 링크된 튜닝 가이드는 V1 기준이다. 설정 이름·기본값·지원 기능은 적용할 버전에서 확인하고, 0.75·seq1 같은 실험값을 다른 환경에 그대로 적용하지 않는다.

결론

한 사용자·짧은 채팅·6GB GPU라는 조건에서 1.7B FP16을 유지하고 메모리와 캐시 설정을 조정하는 편이 합리적이었다. 첫 응답은 빨라졌고 메모리 여유도 늘었지만, 생성 속도는 거의 그대로다. 다음 과제는 최종 Gateway 경로 재측정, 캐시 단독 비교, 컨트롤 플레인 저장 지연 원인 분리다.

내 서비스에 적용할 때 가져갈 순서

  1. 요청 형태와 목표부터 정한다. 입력·출력 길이, 동시성·도착률, 공유 prefix 비율, 품질 과제와 목표 지연을 기록한다. 채팅과 일괄 문서 생성에 같은 목표를 쓰지 않는다.
  2. 고정된 baseline을 만든다. 이미지 digest, 모델·토크나이저 revision, chat template, dtype, context, sampling·thinking 설정을 남긴다. 입력은 같은데 출력 예산이 달라진 비교를 피한다.
  3. 병목 가설에 맞춰 하나씩 바꾼다. 반복 입력이면 캐시, 대기열이면 스케줄링, KV 부족이면 메모리·동시성, 생성 지연이면 커널·graph·speculation을 후보로 둔다. GPU 사용률 하나만으로 원인을 확정하지 않는다.
  4. raw와 실제 API에서 다시 잰다. warm-up과 측정 구간을 분리하고 반복한다. TTFT·TPOT·E2E·실패율·메모리·품질을 함께 보며, 대기열을 보려면 고정 동시성 외에 도착률 기반 부하도 추가한다.
  5. 선택한 버전을 배포하고 실패 경로까지 닫는다. CI는 코드·API 계약을, 배포 후 검사는 실제 요청을 확인한다. 성능 회귀는 별도 GPU runner나 통제된 사후 실험으로 수행한다. 단일 GPU에서는 측정 부하와 서비스 부하를 섞지 않는다.

Q. TTFT가 줄고 TPOT가 같다면?
A. 첫 응답 이전 구간이 개선된 것이다. prefill 재사용 가능성과 queue·네트워크 시간을 나눠 확인한다. decode 가속이라고 부르지 않는다.

Q. 처리량이 늘었는데 사용자는 더 느리다고 한다면?
A. 요청당 생성 간격과 대기열을 확인한다. 합계 token/s보다 해당 사용자의 지연과 goodput이 중요할 수 있다.

Q. GPU 메모리 사용률을 낮추면 항상 좋은가?
A. 아니다. 엔진 밖의 GPU 메모리 여유는 늘어도 KV 공간이 줄어 preemption·재계산이 늘 수 있다. 이번 실험의 메모리 안전 여유 확보와 다른 환경의 동시 수용량 확대는 다른 목적이다.

Q. Argo CD가 Healthy이면 운영 준비가 끝났나?
A. 아니다. 실제 API·품질·지연·복구를 보장하지 않는다. 이 사례도 응답 성공과 controller 재시작이 동시에 관찰됐다.
